# 04. 사람 판단 — PR 승인·반려 이후

> 이 문서는 **열린 PR 에 사람이 내린 판단을 읽고 무엇을 하는지의 원본**이다 (SSOT §2).
>
> PR 에 진입하기까지는 `docs/harness/03-loop.md` 가 정한다. 이 문서는 **PR 이 열린 뒤**를 다룬다.
>
> 승인과 반려의 판정은 사람이 하고, 이 문서는 **그 결과로 무엇을 하는지** 정한다.

---

## 1. 역할과 경계

이 문서가 정하는 것은 다음과 같다.

* 무엇이 승인이고 무엇이 반려인가
* 사람의 판단을 기다리는 상태에서 무엇을 하지 않는가
* 반려 코멘트가 갖춰야 할 것
* 반려를 판독한 뒤 구현 루프로 돌아가는 순서
* 이 흐름에서만 생기는 NEEDS_HUMAN 조건

다음은 이 문서가 정하지 않는다.

* 1 attempt 의 정의와 세는 법 → 03 §2.1
* 구현·검증 반복 절차 → 03 §2.2
* PR 진입 조건 → 03 §2.4 (이 문서는 그것을 다시 정의하지 않고 참조한다)
* CI 가 실패했을 때 → 03 §2.5
* 루프 상태 코멘트의 형식 → 03 §3.1
* 재진입 진입점 → 03 §4
* 최대 시도 횟수 → 해당 Issue 의 6번 항목
* 문서·원본 충돌에서 오는 NEEDS_HUMAN → SSOT §4·§6
* Issue 완료 여부 → 해당 Issue 의 종료 조건

---

## 2. 승인과 반려의 신호

> **승인 = Merge. 반려 = Merge 하지 않은 채 Close.**

GitHub 의 Review 기능(Approve · Request changes · `reviewDecision`)은 **신호로 쓰지 않는다.**
승인·반려의 신호는 PR 의 상태 하나뿐이다. 두 개의 신호원을 두지 않는다.

판독은 다음 한 줄로 한다.

```bash
gh pr view <번호> --json state,mergedAt,closedAt
```

| 상태 | 판정 입력 | 뜻 |
| --- | --- | --- |
| **판단 대기** | `state: OPEN` + CI PASS | 사람이 아직 판단하지 않았다 (§3) |
| **승인** | `state: MERGED` | 사람이 승인했다 (§4) |
| **반려** | `state: CLOSED` 이고 `mergedAt: null` | 사람이 반려했다 (§5) |

`OPEN` 인데 CI 가 실패한 상태는 **이 문서의 상태가 아니다.** 03 §2.5 를 따른다.

---

## 3. 판단 대기

03 §2.4 의 네 조건을 충족해 PR 이 열렸고 CI 가 PASS 면, 그 PR 은 **사람의 판단을 기다리는 상태**다.

이 상태에서 AI 는 다음을 하지 않는다.

* `gh pr merge` — 승인은 사람의 행위다
* `gh pr close` — 반려는 사람의 행위다
* 판단을 기다리지 않고 다음 상태로 진행하는 것

**막는 것과 막지 못하는 것을 구분한다.**

* 막는다
  * AI 가 스스로 자기 작업을 승인하는 것 — 이 문서가 금지한다
* 막지 못한다
  * **저장소에는 그것을 강제할 장치가 없다.** 브랜치 보호도 룰셋도 없고, AI 와 사람이 같은 계정·같은 토큰을 쓴다.
    머지 기록만으로는 사람이 승인한 것과 AI 가 실행한 것을 구별할 수 없다
  * 이것은 SSOT §6 의 `verify:approve` 와 같은 성격의 **규약**이다. 기계가 아니라 규약이 지킨다

---

## 4. 승인

`state: MERGED` 면 그 PR 의 작업은 끝난 것이다.

PR 본문의 `Closes #<번호>` 때문에 **머지와 동시에 연결된 Issue 가 GitHub 에 의해 자동으로 닫힌다.**
이것을 정상 종료로 받아들인다. Issue 를 따로 닫거나 다시 여는 절차를 두지 않는다.

승인 뒤에 남는 루프는 없다. 상태 코멘트를 추가로 남기지 않는다.

---

## 5. 반려

### 5.1 반려 코멘트 요건

사람은 PR 을 반려할 때 **먼저 코멘트를 남기고, 그다음 Merge 없이 Close 한다.**

코멘트는 다음 형식을 따른다.

```text
**[harness] 반려**

- 반려 사유: <무엇이 문제인가>
- 걸린 종료 조건: <해당 Issue 3번의 어느 조건인가>
```

* 마커 `**[harness] 반려**` 로 시작한다
* `반려 사유` 와 `걸린 종료 조건` 두 가지가 **모두** 있어야 한다
* 코멘트를 남긴 뒤 Close 한다

**브랜치를 함께 삭제하지 않는다.**
`gh pr close -d` 로 head 브랜치를 지우면 그 PR 은 다시 열 수 없고, §6 의 재진입이 성립하지 않는다.

### 5.2 유효성 판정

```text
state: CLOSED 이고 mergedAt: null
    │
    ▼
그 PR 의 코멘트에서 [harness] 반려 마커를 찾는다
    │
    ├─ 마커가 있고 두 항목이 모두 있다 ──→ 유효한 반려 → §6
    │
    ├─ 마커가 없다 ────────────────────→ NEEDS_HUMAN
    │
    └─ 마커는 있으나 항목이 빠졌다 ─────→ NEEDS_HUMAN
```

마커가 붙은 코멘트가 여럿이면 **마지막 것이 현재 반려**다.

```bash
gh pr view <번호> --json comments \
  --jq '[.comments[] | select(.body | startswith("**[harness] 반려**"))] | last'
```

### 5.3 유효하지 않을 때

**AI 는 반려 사유를 추측해서 재구현하지 않는다.**

무효한 반려는 `NEEDS_HUMAN` 이다. 이 조건은 문서끼리 어긋난 것이 아니라 이 흐름을 실행하는 중에만
생기므로 SSOT §4 에 두지 않고 **이 문서가 정한다.** 선언한 뒤의 행동은 SSOT §4 를 따른다.

선언은 03 §3 의 루프 상태 코멘트로 남긴다 (`needs_human: 있음`).

---

## 6. 반려 후 재진입

유효한 반려를 판독하면 다음 순서로 구현 루프에 돌아간다. **순서를 바꾸지 않는다.**

```text
유효한 반려 판독
    │
    ▼
① attempt 를 0 으로 초기화한다
    │
    ▼
② Issue 에 루프 상태 코멘트를 남긴다 (§6.2)
    │
    ▼
③ gh pr reopen <번호>
    │
    ▼
④ 03 §2.2 구현·검증 루프로 복귀한다 — 1 회차부터
    │
    ▼
⑤ 03 §2.4 를 다시 충족하면 판단 대기로 돌아간다 (§7)
```

**②가 ③보다 앞선다.** reopen 이 먼저 되면 PR 이 다시 `OPEN` 이 되어, 그사이 세션이 끊기면
다음 세션이 이 상태를 §3 판단 대기로 오독한다. 기록이 먼저 남아야 그 창이 닫힌다.

### 6.1 attempt

**사람 반려는 attempt 를 0 으로 초기화한다.**

반려는 구현 접근이나 요구 해석 자체가 달라질 수 있는 새로운 피드백이므로,
이전 시도의 잔여 횟수를 이어받지 않는다. 재구현은 1 회차부터 다시 센다.

* CI 실패로 로컬 루프에 복귀하는 경우는 초기화하지 않는다 — 그것은 03 §2.5 가 정한다
* 초기화 뒤에도 최대 시도 횟수는 **해당 Issue 의 6번 항목**을 그대로 다시 쓴다
* 반려 횟수 자체에는 상한을 두지 않는다. 반려는 매번 사람의 행위이므로 사람이 통제한다

### 6.2 Issue 기록

형식의 원본은 03 §3.1 이다. **필드를 늘리지 않는다.**

```text
**[harness] 루프 상태**

- attempt: 0
- last_verify: <반려 직전 마지막 verify 결과>
- needs_human: 없음

사람 반려로 구현 루프에 재진입했다. attempt 를 0 으로 초기화했다.
`last_verify` 는 반려 직전에 마지막으로 얻은 결과이며, 지금 상태가 아니다.
반려 사유: #<PR번호> 의 `**[harness] 반려**` 코멘트 — <URL>
```

* `attempt` 는 `0` 이다
* `last_verify` 는 **반려 직전의 마지막 값을 그대로 옮긴다.** 재진입은 verify 를 새로 돌린 것이 아니다.
  값의 형식은 03 §3.1 을 따른다 — `PASS` 또는 `FAIL (단계명)`. 고정된 값이 아니다.
  판단 대기에 있던 PR 이면 대개 `PASS` 지만, CI 실패 복귀 중에 반려되면 `FAIL (단계명)` 이다.
  그리고 `PASS` 라고 해서 지금 PR 에 진입할 수 있다는 뜻이 아니다 (§7)
* `needs_human` 은 `없음` 이다. 유효한 반려는 사람의 판단이 이미 내려진 것이다
* **반려 사유 원문을 Issue 에 옮겨 적지 않는다.** 원본은 PR 코멘트이고, Issue 에는 참조만 남긴다

이 기록은 03 §3.2 가 정한 두 계기(verify 결과 직후 · NEEDS_HUMAN 선언) 외에
**이 문서가 추가하는 세 번째 계기**다. 나머지 기록 규칙은 03 §3.2 를 그대로 따른다.

### 6.3 reopen

**reopen 은 AI 가 실행한다.** Merge 와 Close 만 사람의 행위다.

```bash
gh pr reopen <번호>
```

* **새 PR 을 만들지 않는다.** 재구현 결과는 같은 PR 에 이어서 반영한다
* reopen 이 실패하면 (대개 head 브랜치가 삭제된 경우) `NEEDS_HUMAN` 이다.
  AI 가 새 브랜치나 새 PR 로 우회하지 않는다

---

## 7. 다시 판단 대기로

재구현이 끝났다고 해서 자동으로 판단 대기가 되지 않는다.

**판단 대기 여부는 PR 상태로 판정하지 않는다.** reopen 된 PR 은 재구현 중에도 `OPEN` 이라,
`OPEN` 하나만으로는 §3 과 구별되지 않는다.

판정은 **03 §2.4 의 네 조건**으로 한다.

* 4 번(`Closes #<번호>`)은 같은 PR 을 다시 쓰므로 이미 충족돼 있다
* 1~3 번을 다시 충족하면 그때 판단 대기로 돌아간다
* 특히 3 번 — 종료 조건 충족 결과를 해당 Issue 에 다시 코멘트한다

## 8. 이 문서가 정하지 않는 것

| 무엇 | 어디를 보는가 |
| --- | --- |
| 1 attempt 의 정의 · 세는 법 | `docs/harness/03-loop.md` §2.1 |
| 구현·검증 반복 · 멈추는 조건 | `docs/harness/03-loop.md` §2.2·§2.3 |
| PR 진입 조건 | `docs/harness/03-loop.md` §2.4 |
| CI 실패 후 복귀 | `docs/harness/03-loop.md` §2.5 |
| 루프 상태 코멘트의 형식 | `docs/harness/03-loop.md` §3.1 |
| 세션이 바뀌었을 때의 진입점 | `docs/harness/03-loop.md` §4 |
| 최대 시도 횟수 | 해당 Issue 의 6번 항목 |
| 무엇을 통과해야 검증된 것인가 | `docs/harness/02-verification.md` |
| 문서·원본 충돌의 NEEDS_HUMAN 처리 | `docs/harness/01-ssot.md` §4·§6 |

이 문서는 **사람이 이미 내린 판단을 읽고 무엇을 하는지**만 정한다.

무엇이 좋은 구현인지, 반려가 타당한지는 판단하지 않는다.
