# 02. 검증 하네스 — 골격

> 이 문서는 **무엇을 통과해야 검증된 것인지**를 정한다. 검증 규칙의 원본이다 (SSOT §2·§3).
>
> `scripts/verify/`와 `package.json`의 `verify` 스크립트는 원본이 아니라 **집행 수단**이다.
> 이 문서가 정한 것을 기계가 실행할 수 있는 형태로 옮긴 것이다.
> **둘이 어긋나면 이 문서가 맞고, 고칠 대상은 코드다.**
>
> 대신 이 문서는 실행되지 않으므로 **스스로 실패하지 못한다.**
> 여기 적혔지만 스크립트가 검사하지 않는 규칙은 `npm run verify`로 걸리지 않는다.
> 그런 규칙은 없는 규칙이 아니라 **집행되지 않는 규칙**이며, §7대로 스크립트를 채워서 메운다.

---

## 1. 전부 한 줄이다

```bash
npm run verify
```

로컬에서 돌리는 것과 CI가 돌리는 것이 같은 명령이다.

CI는 검사를 새로 정의하지 않고 이 한 줄을 한 번 더 돌릴 뿐이다.

---

## 2. 단계와 순서

단계와 순서는 이 문서가 정한다. `package.json`의 `verify` 스크립트가 여기에 맞춰져 있어야 한다.

| # | 단계           | 명령                         | 무엇을 보는가                                | 규칙이 온 곳                           |
| - | ------------ | -------------------------- | -------------------------------------- | --------------------------------- |
| 1 | Protected    | `npm run verify:protected` | 보호 경로가 승인 없이 바뀌었는지                     | `docs/harness/01-ssot.md` §6      |
| 2 | Prepare      | `npm run verify:prepare`   | (검사 아님) 검증 전용 DB와 Prisma 클라이언트를 새로 만든다 | —                                 |
| 3 | Types        | `npm run typecheck`        | `tsc --noEmit`                         | TypeScript 설정                     |
| 4 | Lint         | `npm run lint`             | `eslint`                               | `eslint.config.mjs`               |
| 5 | Architecture | `npm run verify:arch`      | 재고 변경이 `applyMovement()`를 거치는지         | `docs/06-architecture.md` §2·§4.1 |
| 6 | Test         | `npm run verify:test`      | 도메인 규칙이 실제 DB 위에서 성립하는지                | `docs/01-requirements.md`         |
| 7 | Build        | `npm run build`            | `prisma generate && next build`        | —                                 |

단계는 `&&`로 이어져 있다. **첫 실패에서 멈춘다.**

### 순서에 이유가 있다

* **Protected가 맨 앞인 이유** — 검사 자신이 무력화됐는지를 먼저 본다.
  `scripts/verify/`도 보호 경로이므로, 검사를 느슨하게 고친 변경은 나머지 단계가 돌기 전에 걸린다.

* **Prepare가 Types 앞인 이유** — Prisma 클라이언트는 생성물이다.
  생성되지 않은 상태에서는 타입 검사부터 실패할 수 있다.

* **Architecture가 Types 뒤인 이유** — 먼저 일반적인 타입 오류를 제거한 뒤, 타입 시스템만으로는 표현할 수 없는 이 저장소의 구조 규칙을 검사한다.

---

## 3. 주요 검사가 잡는 것과 못 잡는 것

검사마다 사각지대가 있다. 한 검사로 모든 잘못을 잡으려 하지 않고 서로 다른 층에서 보완한다.

### Protected

* **잡는다** — 승인 없이 섞여 들어간 원본 변경, 검사 자신을 무력화하는 변경
* **못 잡는다** — 사람이 내용을 보지 않고 승인하는 것

**승인은 검토를 대신하지 않는다** (SSOT §6).

승인 여부는 git 이력이 아니라 **보호 파일 내용의 해시**로 판단한다 (`scripts/verify/protected.json`).

사람이 승인할 때 현재 내용을 해시로 기록하고, 검증할 때 현재 파일의 해시와 승인된 해시가 같은지 비교한다.

그래서 전체 git 이력이 없어도 승인 여부를 판단할 수 있고, 얕은 클론인 CI에서도 같은 검사를 수행할 수 있다.

### Types

TypeScript가 표현할 수 있는 타입 오류를 잡는다.

하지만 타입이 맞는 것과 이 저장소의 구조 규칙을 지키는 것은 같은 일이 아니다.

예를 들어 `PrismaClient`는 `PrismaTx`에 구조적으로 대입될 수 있다.

즉 다음처럼 **트랜잭션이 아닌 클라이언트를 넘겨도 타입 검사는 통과할 수 있다.**

```ts
applyMovement(db, ...)
```

이것이 Architecture 검사가 따로 있는 이유다.

### Architecture

소스 텍스트를 대상으로 하는 정적 검사다. 주석 속 예시 코드에 걸리지 않도록 주석은 제거하고 본다.

* 앱 코드(`src/`) — `lot` / `movement` 직접 쓰기 일절 금지. 통로는 `src/lib/stock.ts` 하나다.
* 시드·테스트·도구(`prisma/`, `tests/`, `scripts/`) — 픽스처 정리용 `delete`만 허용하고, 재고를 만드는 쓰기는 금지한다.
* 통로 자신(`src/lib/stock.ts`) — 직접 쓰기는 허용되지만 트랜잭션 규칙은 똑같이 적용받는다.
* **못 잡는다** — 동적 접근이나 변수를 거친 우회. 정규식이 보는 것은 소스 텍스트뿐이다.

### Test

실제 SQLite DB 위에서 돈다. 목(mock)이 아니다.

현재 다루는 축은 세 가지다.

* FEFO/LEFO 배분
* 재고 불변식
* 팝업 정산

무엇이 테스트되고 있는지의 원본은 `tests/` 자신이다.

이 문서에 테스트 목록을 복사해 두지 않는다.

## 4. 검증 전용 DB

검증은 개발용 DB를 건드리지 않는다.

|    | 개발                            | 검증                    |
| -- | ----------------------------- | --------------------- |
| 파일 | `prisma/dev.db`               | `prisma/verify.db`    |
| 준비 | 없으면 만든다 (`npm run db:ensure`) | **매 실행마다 지우고 새로 만든다** |

`verify:prepare`가 `verify.db`를 삭제한 뒤 `scripts/ensure-db.ts`를 돌린다.

그 안에서 다음 순서로 준비한다.

```text
마이그레이션
    ↓
Prisma 클라이언트 생성
    ↓
시드
```

매번 지우므로 **이전 `npm run verify` 실행이 남긴 상태가 다음 실행에 새지 않는다.**

적어도 이전 검증 실행의 잔여 DB 상태 때문에 테스트가 우연히 통과하지는 않는다.

DB 파일은 커밋하지 않는다. 바이너리라 병합이 어렵고 코드의 스키마와 어긋날 수 있다.

---

## 5. CI

CI의 원본은 `.github/workflows/verify.yml`이다.

* **언제** — `main` 푸시, 그리고 모든 PR
* **무엇** — `npm ci` 후 `npm run verify` 한 줄
* **동시성** — 같은 브랜치에 새 커밋이 오면 진행 중인 실행을 취소한다
* **체크아웃** — Protected가 내용 해시로 판단하므로 전체 git 이력이 필요하지 않다
* **환경 변수** — `DATABASE_URL`은 검증 전용 파일, `SESSION_SECRET`은 CI 전용 더미값을 사용한다. 실제 비밀이 아니며 저장소 시크릿을 쓰지 않는다

CI는 검사를 추가하지도 빼지도 않는다.

```text
로컬
npm run verify
      │
      │ 같은 명령
      ▼
CI
npm run verify
```

로컬에서 통과한 것이 CI에서 실패하면 먼저 **로컬 검증이 깨끗한 상태에서 실행됐는지** 확인한다.

그다음 로컬과 CI의 실행 환경 차이를 확인한다.

---

## 6. 실패했을 때

| 실패 단계        | 첫 행동                                                                         |
| ------------ | ---------------------------------------------------------------------------- |
| Protected    | 의도한 변경인지 **사람에게 확인한다.** 의도했으면 사람이 승인하고, 아니면 변경을 되돌린다                         |
| Prepare      | 스키마·마이그레이션·시드를 본다. 검증 로직 문제가 아니다                                             |
| Types / Lint | 코드를 고친다. 규칙을 끄지 않는다                                                          |
| Architecture | **코드를 고친다.** 재고 변경을 `applyMovement()` 안으로 옮긴다. 실패 메시지가 위반 위치와 근거 원본을 함께 출력한다 |
| Test         | 실패 결과에 맞춰 테스트를 고치지 않는다. 먼저 구현이 원본 규칙을 위반했는지 확인한다                             |
| Build        | 생성물·설정을 본다                                                                   |

원칙은 하나다.

> **검사를 통과시키기 위해 검사를 고치지 않는다.**

검사가 원본 규칙과 어긋났다고 판단되면 임의로 고치지 말고 **사람에게 알린다** (§7, SSOT §6).

`npm run verify:approve`는 **사람의 행위다.**

AI는 사람의 명시적 요청 없이 실행하지 않는다.

## 7. 검증 규칙을 바꿀 때

이 문서와 `scripts/verify/`는 **둘 다** 보호 경로다. 조용히 바뀌지 않는다.

**규칙 자체를 이 문서에서 새로 만들지 않는다.**

도메인 규칙의 원본은 `docs/01-requirements.md`, 구조 규칙의 원본은 `docs/06-architecture.md`다.

이 문서는 그 규칙을 *무엇을 통과해야 하는가*로 옮기고,
`scripts/verify/`는 그중 기계로 판정할 수 있는 것을 다시 코드로 옮긴다.

각 스크립트는 자신이 강제하는 규칙의 출처를 파일 상단에 인용한다.

변경 순서는 다음과 같다.

1. **사람이 요청한다.**
   SSOT §6에 따라 AI가 스스로 시작하지 않는다.

2. 규칙이 도메인·구조에서 온 것이면 **그 원본 문서를 먼저 고친다.**

3. **이 문서를 고친다.** 검증 규칙의 원본은 여기다.

4. `scripts/verify/`와 `package.json`의 `verify` 스크립트를 이 문서에 맞추고,
   스크립트 상단의 원본 인용도 함께 맞춘다.

5. `npm run verify:approve -- "왜 바꾸는지"`로 승인한다.

6. 승인 기록(`scripts/verify/protected.json`)을 **같은 커밋에 담는다.** 그래야 CI에서도 같은 승인을 확인할 수 있다.

**3번과 4번 사이가 벌어지면** 규칙은 있으나 집행되지 않는 상태가 된다.

그 어긋남을 잡아 주는 자동 검사는 없다. 같은 커밋에서 함께 고치는 것으로만 막는다.

이 문서에 규칙을 적고 스크립트를 미루는 것은 규칙을 만든 것이 아니라 **빚을 진 것이다.**

---

## 8. 이 문서가 정하지 않는 것

| 무엇                                                | 어디를 보는가                                               |
| ------------------------------------------------- | ----------------------------------------------------- |
| 검사가 실제로 어떻게 구현됐는가                                 | `scripts/verify/`                                     |
| 개별 테스트 케이스                                        | `tests/` — 이 문서는 축만 정하고 케이스를 세지 않는다                    |
| 도메인 규칙 · 구조 규칙                                    | `docs/01-requirements.md` · `docs/06-architecture.md` |
| **Issue → 구현 → 검증 → PR → CI → Review → Merge 순서** | **원본 없음** (SSOT §5)                                   |

마지막 줄을 특히 주의한다.

이 문서는 **무엇을 통과해야 검증된 것인지**만 정한다.

**언제 무엇을 하는지**는 정하지 않는다.

구현·검증 루프의 원본은 아직 없다.

지금까지의 관행을 규칙인 것처럼 말하지 않는다.

그전까지는 **"정해진 바 없음"**이 정확한 답이다.
