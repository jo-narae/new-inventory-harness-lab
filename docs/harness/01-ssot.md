# 01. 하네스 SSOT — 원본 등록부


> 이 문서는 **각 영역의 원본이 어디인지**만 정한다.
> 실제 규칙과 내용은 각 원본에서 관리한다.


---


## 1. 원칙


1. **한 영역의 원본은 하나다.**
2. 같은 내용이 여러 곳에 있으면 **등록된 원본을 기준으로 판단한다.**
3. 원본과 사본이 다르면 **원본을 유지하고 사본을 수정한다.**
4. 아직 원본이 없는 영역은 임의의 문서를 기준으로 삼지 않는다.
5. **충돌은 AI가 해소하지 않는다.** 처리 방법은 §4를 따른다.
6. **SSOT 수정은 사람이 시작한다.** AI는 요청받았을 때만 고친다. §6을 따른다.

## 3. 영역별 경계


### 재고 도메인


**원본:** `docs/01-requirements.md`


다음을 판단할 때 사용한다.


* 재고의 정의와 거점 종류
* 기능 요구사항
* 재고 증감 규칙
* FEFO / LEFO 등 도메인 규칙
* 비기능 요구사항과 완료 기준


구현 구조는 이 문서에서 판단하지 않는다.


---


### 아키텍처


**원본:** `docs/06-architecture.md`


다음을 판단할 때 사용한다.


* 코드 구조와 책임
* 핵심 로직의 구현 방식
* 상태 및 쓰기 흐름
* 아키텍처 결정


도메인 규칙 자체는 `docs/01-requirements.md`를 따른다.


---




### 검증 규칙


**원본:** `docs/harness/02-verification.md`


무엇을 통과해야 검증된 것인지는 이 문서가 정한다.
단계와 순서, 각 단계가 무엇을 보는지, 실패했을 때 무엇을 하는지가 여기서 결정된다.


`scripts/verify/`는 원본이 아니라 **집행 수단**이다.
검증 원본이 정한 것을 기계가 실행할 수 있는 형태로 옮긴 것이고, `npm run verify`가 그것을 돌린다.
각 스크립트는 자신이 강제하는 규칙의 출처를 파일 상단에 인용한다.


규칙 자체를 검증 원본에서 새로 만들지 않는다 — 도메인 규칙은 `docs/01-requirements.md`,
구조 규칙은 `docs/06-architecture.md`가 원본이다.
`docs/harness/02-verification.md`는 그것들을 **무엇을 통과해야 하는가**로 옮긴 것이다.


**문서와 스크립트가 어긋나면 문서가 맞다.** 고칠 대상은 스크립트다.


이 배치에는 대가가 있다. 원본이 실행되지 않으므로 **원본은 실패하지 않는다.**
스크립트가 검사하지 않는 규칙이 문서에 있어도 `npm run verify`는 통과한다.
그런 규칙은 없는 규칙이 아니라 **집행되지 않는 규칙**이고, 스크립트를 채워서 메운다.
이 어긋남을 자동으로 잡아 주는 검사는 없다 — 둘을 같은 커밋에서 함께 고치는 것으로만 막는다.


다른 문서의 QA 체크리스트나 테스트 목록은 검증 원본이 아니다.


---


### 개별 작업


**원본:** GitHub Issue


Issue는 다음을 정의한다.


* 무엇을 변경하는가
* 왜 변경하는가
* 무엇을 만족하면 완료인가


도메인 규칙이나 아키텍처 결정을 Issue에서 새로 정의하지 않는다.


Issue가 기존 원본과 충돌하면 **AI가 어느 쪽이 맞는지 판단하지 않는다.**
`NEEDS_HUMAN`을 선언하고 사람의 판단을 받는다 (§4).


새로운 규칙이나 구조 결정이 필요하면 해당 원본을 먼저 수정한 뒤 Issue에서 참조한다.


---


## 4. 충돌 처리


문서끼리 말이 다를 때 무엇을 하는지 정한다.


| 충돌 | 처리 |
| ---------------- | ------------------------------------------- |
| 참고 문서 ↔ SSOT | **SSOT를 따른다.** 참고 문서를 사본으로 보고 SSOT에 맞춰 고친다. |
| Issue ↔ SSOT | **`NEEDS_HUMAN` 선언.** 사람의 판단을 받는다. |
| SSOT ↔ SSOT | **`NEEDS_HUMAN` 선언.** 사람의 판단을 받는다. |


**AI는 충돌을 자신의 판단으로 해소하지 않는다.**
어느 쪽이 더 그럴듯한지, 어느 쪽이 더 최근인지, 어느 쪽이 코드와 맞는지로 정하지 않는다.
AI가 스스로 처리하는 것은 첫 줄(참고 문서 ↔ SSOT)뿐이고, 그마저도 범위는 사본을 SSOT에 맞추는 것까지다.


### NEEDS_HUMAN 선언 방법


선언할 때 다음 세 가지를 함께 적는다.


1. 충돌한 두 곳의 위치 — 파일과 섹션, 또는 Issue 번호
2. 각각이 무엇이라고 말하는지 — 원문 인용
3. 무엇이 정해져야 진행할 수 있는지


선언한 뒤에는 **그 판단에 의존하는 작업을 진행하지 않는다.**
같은 작업이라도 그 판단과 무관한 부분은 계속 진행할 수 있고, 무엇을 남겨 뒀는지 밝힌다.


충돌이 해소되면 §6에 따라 원본을 먼저 고친다.


---


## 5. 아직 원본이 없는 영역


### 구현·검증 루프


현재 원본 없음.


추후 다음 흐름을 명시하는 원본을 만든다.


`Issue → 구현 → 검증 → PR → CI → Review → 사람 판단 → Merge`


세부 순서와 실패·재시도 규칙은 해당 원본이 만들어질 때 정의한다.


---


## 6. 원본 변경 규칙


### 수정은 사람이 시작한다


**AI는 스스로 SSOT를 수정하지 않는다. 사람이 요청할 때만 수정한다.**


사람이 요청하면 받아준다. 요청이 기존 SSOT와 어긋나더라도 AI가 거부하거나 임의로 조정하지 않는다.
어긋난다는 사실을 먼저 말하고, 요청대로 반영한다. 무엇이 맞는지는 사람이 정한다.


SSOT가 틀렸다고 판단되면 고치지 말고 **말한다.**
어디가 어떻게 틀렸는지, 무엇으로 바꾸면 되는지까지 제안하되 수정은 요청을 받은 뒤에 한다.


코드·Issue·PR 코멘트에서 알게 된 사실만으로 SSOT를 갱신하지 않는다.
그것들은 원본이 아니다.


### 보호 경로와 승인


원본이 조용히 바뀌면 안 된다. 아래는 **보호 경로**이며, 바꾸려면 사람의 승인이 필요하다.


* `docs/01-requirements.md`
* `docs/06-architecture.md`
* `docs/harness/01-ssot.md`
* `docs/harness/02-verification.md`
* `prisma/schema.prisma`
* `scripts/verify/` 안의 모든 `.ts`


`npm run verify`의 **첫 단계**인 Protected 가 이를 검사한다.
승인된 내용과 지금 내용이 다르면 나머지 단계를 돌리기 전에 실패한다.


**승인 방법**


```
npm run verify:approve -- "왜 바꾸는지"
```


지금 내용을 승인된 기준선으로 기록한다 (`scripts/verify/protected.json`).
이 기록을 **변경과 같은 커밋에 담아야** CI 에서도 통과한다.
승인은 git 이력이나 브랜치가 아니라 **내용 해시**로 남으므로,
얕은 클론에서도 로컬과 CI 가 같은 결과를 낸다.


**승인에는 사유가 남는다.** 사유를 빠뜨린 승인은 같은 명령에 사유를 붙여 다시 실행해 메운다 —
보호 경로 변경이 없어도 사유만 갱신되며, 무엇을 승인했는지(해시)는 그대로다.


**승인은 사람의 행위다.**
AI 는 `verify:approve` 를 사람의 명시적 요청 없이 실행하지 않는다.
보호 경로를 고쳐야 한다고 판단되면, 고치기 전에 말한다 (위 "수정은 사람이 시작한다").


**우회 — 사람이 말하면 넘어간다**


```
PROTECTED_OK="왜 넘어가는지" npm run verify
```


승인되지 않은 보호 경로 변경이 있어도 통과한다. **로컬과 CI 에서 똑같이 동작한다.**
무엇을 넘겼는지와 사유는 그 실행의 출력에만 남고, `protected.json` 은 갱신되지 않는다.
저장소에 남는 기록은 없다 — 남기려면 승인해야 한다.


**우회도 사람의 행위다.**
AI 는 `PROTECTED_OK` 를 사람의 명시적 요청 없이 설정하지 않는다.


이 장치가 막는 것과 막지 못하는 것을 구분한다.


* 막는다 — 의도하지 않은 변경, 검토 없이 조용히 섞여 들어간 변경
* 막지 못한다
  * 사람이 내용을 보지 않고 승인하는 것. **승인은 검토를 대신하지 않는다.**
  * `PROTECTED_OK` 로 넘긴 변경. 승인 없이 main 까지 갈 수 있다
  * **검사 자신을 무력화하는 변경.** 우회가 열려 있는 한 이 검사는 스스로를 지키지 못한다


### 수정 절차


원본을 변경할 때는 다음 순서를 따른다.


1. 변경하려는 영역의 원본을 이 문서에서 확인한다.
2. 해당 원본을 수정한다.
3. 같은 내용을 가진 사본이 있으면 함께 동기화한다.
4. 등록되지 않은 새로운 영역이라면 **원본을 먼저 정한 뒤 이 등록부에 추가한다.**


> **판단 기준:**
> 무엇이 맞는지 모르겠으면 내용을 비교하기 전에 **어느 것이 원본인지 먼저 확인한다.**
