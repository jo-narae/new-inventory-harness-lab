# 03. 구현·검증 루프 — 판정 이후의 반복

> 이 문서는 **로컬 구현·검증 반복의 원본**이다 (SSOT §2).
>
> 검증의 판정은 `docs/harness/02-verification.md`가 정하고, 이 문서는 **그 결과로 무엇을 하는지** 정한다.
>
> PR 진입 조건과 CI 실패 후 복귀까지 다룬다. PR 이 열린 뒤 사람의 승인·반려는
> `docs/harness/04-human-decision.md` 가 정한다.

---

## 1. 역할과 경계

이 문서가 정하는 것은 다음과 같다.

* 1 attempt의 정의
* 구현과 검증을 반복하는 방법
* 반복을 멈추고 사람에게 넘기는 조건
* PR 에 진입할 수 있는 조건
* CI 가 실패했을 때 로컬 루프로 복귀하는 조건
* 루프를 실행하는 중에 NEEDS_HUMAN 이 되는 조건
* 루프 상태를 기록하는 방법
* 세션이 바뀌었을 때 재진입하는 방법

다음은 이 문서가 정하지 않는다.

* `npm run verify`의 단계·순서·판정 → 02
* 문서·원본 충돌에서 오는 NEEDS_HUMAN → SSOT §4·§6
* Issue 완료 여부 → 해당 Issue의 종료 조건
* PR 승인·반려와 그 이후 → `docs/harness/04-human-decision.md`

---

## 2. 구현·검증 루프

### 2.1 1 attempt

> **1 attempt = 구현을 변경한 뒤 `npm run verify`를 한 번 실행해 결과를 얻은 것.**

* PASS와 FAIL 모두 1 attempt다.
* 첫 실행부터 1 attempt다.
* 최대 시도 횟수가 3이면 구현을 변경한 뒤 돌리는 로컬 `npm run verify`도 최대 3회다.
* 중간에 끊기거나 실행 자체가 시작되지 않은 경우는 세지 않는다.
* 실패 단계에 따라 attempt 소모 여부를 나누지 않는다.
* CI 의 `npm run verify` 실행은 세지 않는다.
* CI 실패를 확인하려고 같은 커밋에서 돌린 로컬 실행은 구현 변경이 없으므로 세지 않는다.

최대 시도 횟수의 원본은 **해당 Issue의 6번 항목**이다.

attempt 를 0 으로 되돌리는 조건은 이 문서가 정하지 않는다.
사람 반려로 인한 초기화는 `docs/harness/04-human-decision.md` §6.1 이 정한다.

### 2.2 반복 절차

```text
구현 변경
    │
    ▼
npm run verify
    │
    └─ 결과를 얻음 → attempt +1 → 상태 기록 (§3)
                         │
                         ├─ PASS ───────────────→ 로컬 루프 종료
                         │
                         └─ FAIL
                              │
                              ├─ NEEDS_HUMAN ───→ 즉시 이탈
                              │
                              ├─ 최대 횟수 도달 ─→ 사람에게 넘김
                              │
                              └─ 그 외 ─────────→ 구현 수정 후 반복
```

FAIL 후 다시 구현하는 조건은 다음 세 가지가 모두 참일 때다.

1. 결과가 FAIL이다.
2. `attempt`가 최대 시도 횟수보다 작다.
3. NEEDS_HUMAN에 해당하지 않는다.

무엇이 실패했고 무엇을 확인해야 하는지는 02 §6을 따른다.

### 2.3 멈추는 조건

루프는 다음 세 경우에 멈춘다.

* **PASS** → 로컬 구현·검증 루프를 끝낸다. PR 진입은 §2.4를 따른다.
* **최대 시도 횟수 도달** → 반복을 중단하고 사람에게 넘긴다.
* **NEEDS_HUMAN** → 즉시 루프에서 이탈한다.

PASS는 **Issue 완료를 의미하지 않는다.**

Issue 완료 여부는 해당 Issue의 종료 조건으로 판단한다.

문서·원본 충돌에서 오는 NEEDS_HUMAN 과 이탈 시 행동은
새로 정의하지 않고 **SSOT §4·§6을 따른다.**

루프를 실행하는 중에 생기는 NEEDS_HUMAN 조건은 이 문서의 해당 절이 직접 정의한다.

### 2.4 PR 진입

PASS로 루프가 끝났다는 것만으로 PR로 넘어가지 않는다.

다음 네 조건이 **모두** 참일 때 PR에 진입한다.

1. 마지막 로컬 `npm run verify`가 PASS다.
2. 해당 Issue의 종료 조건이 전부 충족됐다.
3. 종료 조건의 충족 결과를 해당 Issue에 코멘트했다.
4. PR 본문이 해당 Issue를 `Closes #<번호>`로 연결한다.

하나라도 아니면 PR을 열지 않는다.

3번은 §3의 루프 상태 코멘트와 다른 것이다. 새 형식이나 마커를 정하지 않으며,
무엇을 근거로 종료 조건이 충족됐다고 보는지 남기는 것까지가 규칙이다.

4번은 PR을 연 직후에 확인한다. 본문에 문자열이 있는지가 아니라 **GitHub이 링크로 인식했는지**를 본다.

```bash
gh pr view <번호> --json closingIssuesReferences
```

비어 있으면 연결되지 않은 것이다. 본문을 고쳐 링크가 잡히게 한다.

종료 조건의 원본은 **해당 Issue**다. 이 문서는 그것을 판단하지 않는다.

PR이 열리면 CI가 `npm run verify`를 돌린다. 무엇이 언제 도는지는 02 §5가 정한다.

CI가 PASS면 그 PR은 사람의 판단을 기다리는 상태가 된다.
그 뒤는 `docs/harness/04-human-decision.md`가 정한다.

### 2.5 CI가 실패했을 때

CI FAIL을 받으면 **같은 커밋에서** 로컬 `npm run verify`를 돌려 재현되는지 확인한다.

```text
CI FAIL
    │
    ▼
같은 커밋에서 로컬 npm run verify        ← attempt 아님
    │
    ├─ CI와 같은 단계에서 같은 실패 ──→ §2.2 루프로 복귀
    │
    ├─ 로컬은 PASS ─────────────────→ NEEDS_HUMAN
    │
    └─ 다른 실패가 났다 ─────────────→ NEEDS_HUMAN
```

**동일하게 재현된 경우만 복귀다.** 로컬이 PASS거나 다른 실패가 나면 재현된 것이 아니다.

재현되지 않은 경우를 NEEDS_HUMAN 으로 보는 것은 **이 문서가 정한다.**
문서끼리 어긋난 것이 아니라 루프를 실행하는 중에만 생기므로 SSOT §4에 두지 않는다.
선언한 뒤의 행동은 SSOT §4를 따른다.

복귀한 뒤에는 §2.2를 그대로 따른다.
attempt는 **구현을 수정하고 다시 `npm run verify`를 실행한 것부터** 이어서 센다.

* 재현 확인 실행은 attempt가 아니다.
* **CI 재현 복귀에서는** attempt를 0으로 초기화하지 않는다.
  사람 반려로 인한 초기화는 다른 경우이며 `docs/harness/04-human-decision.md` §6.1이 정한다.
* 이미 최대 시도 횟수를 소진했다면 복귀 즉시 §2.3에 따라 사람에게 넘긴다.

## 3. 상태 기록

세션이 바뀌어도 루프를 이어받을 수 있도록 상태를 **해당 GitHub Issue의 코멘트**에 기록한다.

### 3.1 형식

```text
**[harness] 루프 상태**

- attempt: 2
- last_verify: FAIL (Test)
- needs_human: 없음
```

필드는 세 개만 사용한다.

* `attempt` — 지금까지 완료한 attempt 수
* `last_verify` — `PASS` 또는 `FAIL (단계명)`
* `needs_human` — `있음` 또는 `없음`

`last_verify`는 **마지막으로 얻은 verify 결과**다. 그 뒤의 상태를 보증하지 않는다 —
결과를 얻은 뒤 구현이나 상황이 바뀌었어도 값은 그대로 남는다.

최대 시도 횟수는 기록하지 않는다. **해당 Issue의 6번 항목에서 읽는다.**

`needs_human: 있음`이면 무엇이 어긋났는지 함께 기록한다.
문서·원본 충돌이면 SSOT §4의 선언 형식을 그대로 따른다.

* 어긋난 두 곳의 위치
* 각각에서 관찰된 결과
* 무엇이 정해져야 진행할 수 있는지

### 3.2 기록 규칙

1. verify 결과를 얻은 직후 새 상태 코멘트를 추가한다.
2. NEEDS_HUMAN을 선언할 때 새 상태 코멘트를 추가한다.
3. 기존 상태 코멘트는 수정하지 않는다.
4. 같은 마커가 붙은 **마지막 코멘트가 현재 상태**다.
5. 상태 코멘트가 없으면 `attempt: 0`으로 본다.

1·2 외에 코멘트를 추가하는 계기가 하나 더 있다 —
사람 반려로 구현 루프에 재진입할 때다. `docs/harness/04-human-decision.md` §6.2가 정한다.
형식(§3.1)은 그대로이며 필드가 늘지 않는다.

상태 기록은 규약이며 `npm run verify`가 집행하지 않는다.

## 4. 재진입

작업을 시작하거나 이어받을 때마다 다음 순서로 현재 상태를 확인한다.

### 4.1 Issue를 읽는다

해당 Issue에서 다음을 확인한다.

* 종료 조건
* 최대 시도 횟수

### 4.2 마지막 루프 상태를 읽는다

```bash
gh issue view <번호> --json comments \
  --jq '[.comments[] | select(.body | startswith("**[harness] 루프 상태**"))] | last'
```

상태 코멘트가 없으면 `attempt: 0`으로 시작한다.

### 4.3 이어갈 수 있는지 판단한다

해당 Issue에 연결된 PR이 이미 있으면 그 PR의 상태를 먼저 본다.
승인·반려 판단이 걸린 상태라면 `docs/harness/04-human-decision.md`를 따른다.
아래 분기는 그 판단이 걸려 있지 않을 때 쓴다.

```text
마지막 루프 상태
    │
    ├─ needs_human: 있음
    │      └─ 해당 판단에 의존하는 작업을 진행하지 않는다
    │
    ├─ attempt >= 최대 시도 횟수
    │      └─ verify를 실행하지 않고 사람에게 넘긴다
    │
    └─ 그 외
           └─ 구현·검증 루프를 이어간다 (§2)
```

`needs_human: 있음`이면 상태 코멘트에 기록된 내용을 사람에게 보여주고, 사람의 판단이 있기 전까지 해당 판단에 의존하는 작업을 진행하지 않는다.
