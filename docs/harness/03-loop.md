# 03. 구현·검증 루프 — 판정 이후의 반복

> 이 문서는 **로컬 구현·검증 반복의 원본**이다 (SSOT §2).
>
> 검증의 판정은 `docs/harness/02-verification.md`가 정하고, 이 문서는 **그 결과로 무엇을 하는지** 정한다.
>
> PR 이후의 흐름은 아직 다루지 않는다.

---

## 1. 역할과 경계

이 문서가 정하는 것은 다음과 같다.

* 1 attempt의 정의
* 구현과 검증을 반복하는 방법
* 반복을 멈추고 사람에게 넘기는 조건
* 루프 상태를 기록하는 방법
* 세션이 바뀌었을 때 재진입하는 방법

다음은 이 문서가 정하지 않는다.

* `npm run verify`의 단계·순서·판정 → 02
* NEEDS_HUMAN이 되는 조건 → SSOT §4·§6, 02 §6
* Issue 완료 여부 → 해당 Issue의 종료 조건
* PR 이후의 흐름 → 아직 원본 없음

---

## 2. 구현·검증 루프

### 2.1 1 attempt

> **1 attempt = 구현을 변경한 뒤 `npm run verify`를 한 번 실행해 결과를 얻은 것.**

* PASS와 FAIL 모두 1 attempt다.
* 첫 실행부터 1 attempt다.
* 최대 시도 횟수가 3이면 `npm run verify`도 최대 3회다.
* 중간에 끊기거나 실행 자체가 시작되지 않은 경우는 세지 않는다.
* 실패 단계에 따라 attempt 소모 여부를 나누지 않는다.

최대 시도 횟수의 원본은 **해당 Issue의 6번 항목**이다.

### 2.2 반복 절차

```text
구현 변경
    │
    ▼
npm run verify
    │
    └─ 결과를 얻음 → attempt +1 → 상태 기록 (§3)
                         │
                         ├─ PASS ───────────────→ 로컬 루프 종료
                         │
                         └─ FAIL
                              │
                              ├─ NEEDS_HUMAN ───→ 즉시 이탈
                              │
                              ├─ 최대 횟수 도달 ─→ 사람에게 넘김
                              │
                              └─ 그 외 ─────────→ 구현 수정 후 반복
```

FAIL 후 다시 구현하는 조건은 다음 세 가지가 모두 참일 때다.

1. 결과가 FAIL이다.
2. `attempt`가 최대 시도 횟수보다 작다.
3. NEEDS_HUMAN에 해당하지 않는다.

무엇이 실패했고 무엇을 확인해야 하는지는 02 §6을 따른다.

### 2.3 멈추는 조건

루프는 다음 세 경우에 멈춘다.

* **PASS** → 로컬 구현·검증 루프를 끝낸다.
* **최대 시도 횟수 도달** → 반복을 중단하고 사람에게 넘긴다.
* **NEEDS_HUMAN** → 즉시 루프에서 이탈한다.

PASS는 **Issue 완료를 의미하지 않는다.**

Issue 완료 여부는 해당 Issue의 종료 조건으로 판단한다.

NEEDS_HUMAN 조건과 이탈 시 행동은 새로 정의하지 않고 **SSOT §4·§6과 02 §6을 따른다.**

## 3. 상태 기록

세션이 바뀌어도 루프를 이어받을 수 있도록 상태를 **해당 GitHub Issue의 코멘트**에 기록한다.

### 3.1 형식

```text
**[harness] 루프 상태**

- attempt: 2
- last_verify: FAIL (Test)
- needs_human: 없음
```

필드는 세 개만 사용한다.

* `attempt` — 지금까지 완료한 attempt 수
* `last_verify` — `PASS` 또는 `FAIL (단계명)`
* `needs_human` — `있음` 또는 `없음`

최대 시도 횟수는 기록하지 않는다. **해당 Issue의 6번 항목에서 읽는다.**

`needs_human: 있음`이면 SSOT §4에서 정한 내용을 함께 기록한다.

* 충돌한 두 곳의 위치
* 각각이 무엇이라고 말하는지
* 무엇이 정해져야 진행할 수 있는지

### 3.2 기록 규칙

1. verify 결과를 얻은 직후 새 상태 코멘트를 추가한다.
2. NEEDS_HUMAN을 선언할 때 새 상태 코멘트를 추가한다.
3. 기존 상태 코멘트는 수정하지 않는다.
4. 같은 마커가 붙은 **마지막 코멘트가 현재 상태**다.
5. 상태 코멘트가 없으면 `attempt: 0`으로 본다.

상태 기록은 규약이며 `npm run verify`가 집행하지 않는다.

---

## 4. 재진입

작업을 시작하거나 이어받을 때마다 다음 순서로 현재 상태를 확인한다.

### 4.1 Issue를 읽는다

해당 Issue에서 다음을 확인한다.

* 종료 조건
* 최대 시도 횟수

### 4.2 마지막 루프 상태를 읽는다

```bash
gh issue view <번호> --json comments \
  --jq '[.comments[] | select(.body | startswith("**[harness] 루프 상태**"))] | last'
```

상태 코멘트가 없으면 `attempt: 0`으로 시작한다.

### 4.3 이어갈 수 있는지 판단한다

```text
마지막 루프 상태
    │
    ├─ needs_human: 있음
    │      └─ 해당 판단에 의존하는 작업을 진행하지 않는다
    │
    ├─ attempt >= 최대 시도 횟수
    │      └─ verify를 실행하지 않고 사람에게 넘긴다
    │
    └─ 그 외
           └─ 구현·검증 루프를 이어간다 (§2)
```

`needs_human: 있음`이면 상태 코멘트에 기록된 내용을 사람에게 보여주고, 사람의 판단이 있기 전까지 해당 판단에 의존하는 작업을 진행하지 않는다.
