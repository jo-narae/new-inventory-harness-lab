# 이슈 하나를 PR 앞까지 처리한다

## 이 스킬은 원본이 아니다

규칙의 원본은 아래 문서들이고, 이 스킬은 **그것을 실행 순서로 옮긴 사본**이다.
이 문서와 원본이 어긋나면 **원본이 맞고, 고칠 대상은 이 스킬이다** (AGENTS.md §4).

| 판단할 것 | 원본 |
| --- | --- |
| 무엇을 통과해야 검증인가 · 실패가 무슨 뜻인가 | `docs/harness/02-verification.md` |
| attempt · 루프 · PR 진입 조건 · CI 실패 후 복귀 | `docs/harness/03-loop.md` |
| PR 승인·반려 판독과 그 이후 | `docs/harness/04-human-decision.md` |
| 충돌 처리 · 보호 경로 · 승인 | `docs/harness/01-ssot.md` §4·§6 |
| 이 작업의 범위와 종료 조건 | 해당 GitHub Issue |

**절 번호를 인용한 곳은 근거다.** 판단이 애매하면 그 절만 열어 확인한다.
작업 시작할 때 문서를 전부 읽지 않는다 — 필요한 갈래에 닿았을 때 그 원본만 읽는다.

## 0. 먼저 지금이 어느 지점인지 판정한다

**이 스킬은 언제나 여기서 시작한다.** "이슈 처리해줘"는 새 작업일 수도, 끊긴 세션의 재개일 수도,
반려된 PR의 재구현일 수도 있다. 셋을 구별하지 않고 진행하면 이미 있는 PR 옆에 새 PR을 만들거나
소진된 attempt를 못 보고 루프를 더 돌게 된다. 03 §4가 재진입을 먼저 판정하라고 정한 이유다.

### 0.1 대상 Issue를 정한다

번호를 들었으면 그 번호를 쓴다. 못 들었으면:

```bash
gh issue list --state open --json number,title,labels
```

* 열린 이슈가 **1개** → 그것으로 진행하되, 번호와 제목을 말하고 시작한다
* **여러 개** → 목록을 보여주고 어느 것인지 묻는다. 임의로 고르지 않는다
* **0개** → 처리할 이슈가 없다고 알리고 멈춘다

### 0.2 Issue에서 두 가지를 읽는다

```bash
gh issue view <번호> --json number,title,body,url
```

* **3번 항목 — 종료 조건.** 이 작업이 언제 끝나는지의 유일한 원본이다
* **6번 항목 — 최대 시도 횟수.** 숫자 하나(1·2·3·5)다

6번 항목의 제목 문구는 이슈마다 다를 수 있다(템플릿이 바뀌었다). `### 6.` 으로 시작하는 절을 찾고,
제목 문구로 매칭하지 않는다.

### 0.3 마지막 루프 상태를 읽는다 (03 §4.2)

```bash
gh issue view <번호> --json comments \
  --jq '[.comments[] | select(.body | startswith("**[harness] 루프 상태**"))] | last'
```

상태 코멘트가 없으면 `attempt: 0`이다 (03 §3.2-5).

### 0.4 연결된 PR이 있는지 본다

```bash
gh pr list --state all --limit 50 --json number,state,mergedAt,headRefName,title,body \
  --jq '[.[] | select((.headRefName | test("issue-<번호>(-|$)")) or (.body | test("[Cc]loses #<번호>\\b")))]'
```

브랜치 이름과 본문의 `Closes #<번호>` 두 곳 중 하나만 걸려도 찾는다.
브랜치 이름 규칙은 원본이 아니라 관행이라(§1), 사람이 다른 이름으로 만든 브랜치도 본문으로 걸린다.

### 0.5 분기

| 지금 상태 | 어디로 |
| --- | --- |
| `needs_human: 있음` | **멈춘다.** 상태 코멘트 내용을 사람에게 보여주고, 그 판단에 의존하는 작업은 하지 않는다 (SSOT §4) |
| PR이 `MERGED` | 승인된 것이다. 그 Issue는 `Closes` 로 이미 닫혔다. 할 일 없음 (04 §4) |
| PR이 `CLOSED` + `mergedAt: null` | **반려다.** → §7 |
| PR이 `OPEN` + CI PASS + 03 §2.4 네 조건 충족 | **판단 대기다.** → §6. merge·close 하지 않는다 |
| PR이 `OPEN` 인데 네 조건 중 하나라도 미충족 | **재구현 중이다.** → §3·§4를 이어간다. **같은 PR을 쓴다** |
| PR이 `OPEN` + CI FAIL | → §5.5 CI 실패 복귀 |
| `attempt >= 최대 시도 횟수` | **verify를 돌리지 않고** 사람에게 넘긴다 (03 §4.3) |
| PR 없음 + attempt 진행 중 | 브랜치를 확인하고 §3 구현부터 이어간다 |
| 아무것도 없음 | 새 작업이다. → §1 |

**`OPEN` 하나로 판단 대기를 판정하지 않는다** (04 §7). 반려로 reopen된 PR도 재구현 중에 계속 `OPEN`이라,
상태만으로는 §6과 구별되지 않는다. 판정은 **03 §2.4 네 조건**으로 한다 — 특히 3번(종료 조건 충족 코멘트)이
가장 최근 재진입 이후에 남아 있는지를 본다. 마지막 루프 상태 코멘트가 `attempt: 0` + 반려 재진입이면
아직 재구현 중이다.

## 1. 브랜치

```bash
git status --porcelain            # 비어 있지 않으면 멈추고 사람에게 무엇이 남았는지 묻는다
git switch main && git pull --ff-only
git switch -c <type>/issue-<번호>-<기능명>
```

작업 트리가 더러운 채로 브랜치를 옮기면 남의 변경이 이 작업에 섞여 들어간다.
비어 있지 않으면 그것이 무엇인지 먼저 확인한다.

* `<type>` — `feat` · `fix` · `docs` · `chore` 중 이슈 성격에 맞는 것
* `<기능명>` — 영문 kebab-case. **02 §3이 정한 전용 테스트 파일명의 `<기능명>`과 같은 값을 쓴다.**
  브랜치·테스트 파일·Issue가 한 이름으로 묶여야 나중에 무엇이 무엇인지 추적된다
* 예) Issue #6 팝업 기한 표시 → `fix/issue-6-popup-expiration`,
  전용 테스트는 `tests/issues/issue-6-popup-expiration.test.ts`

브랜치 이름은 원본이 정한 영역이 아니다 — 저장소 관행이다. 사람이 다른 이름을 지시하면 그것을 따른다.

이미 그 브랜치가 있으면 새로 만들지 말고 그 위에서 이어간다.

## 2. 구현 전에 읽을 것 하나를 고른다

**문서를 전부 읽지 않는다** (AGENTS.md §1). 이슈가 무엇을 묻는지에 따라 하나만 연다.

| 이슈가 이런 것이면 | 이것만 |
| --- | --- |
| 도메인 규칙 · FEFO/LEFO · 재고 증감 · 무엇이 범위 안인가 | `docs/01-requirements.md` |
| 코드 구조 · `applyMovement` · 쓰기 흐름 · 인증 · 동시성 | `docs/06-architecture.md` |
| 데이터 모델 | `prisma/schema.prisma` |

그 원본으로 판단이 안 서면 인접 원본 → 코드(`docs/HANDOVER.md` §6 파일 지도) → **사람에게 묻는다** 순으로 넓힌다.
한 단계에서 답이 나오면 멈춘다.

**Issue가 원본과 어긋나면 어느 쪽이 맞는지 스스로 고르지 않는다.** NEEDS_HUMAN이다 (SSOT §4). → §8

## 3. 구현

### 3.1 전용 테스트를 함께 만든다 (02 §3)

```
tests/issues/issue-<번호>-<기능명>.test.ts
```

**`it` 하나가 Issue 3번 종료 조건의 한 줄에 대응한다.** 그래야 어떤 조건이 깨졌는지
실패 메시지만 보고 알 수 있고, 판정되지 않고 남은 조건이 있는지 눈으로 셀 수 있다.

종료 조건 중 기존 검사로 판정되지 않는 것이 있으면, **그 검사를 만드는 것까지가 이 작업의 범위다.**
문서에는 있으나 집행되지 않는 규칙을 남기지 않기 위해서다.

### 3.2 구조 규칙

재고를 바꾸는 쓰기는 `applyMovement()`를 거친다. `lot`/`movement` 직접 쓰기는 Architecture 단계가 잡는다.
자세한 것은 `docs/06-architecture.md`.

### 3.3 보호 경로를 건드리게 되면 멈춘다 (SSOT §6)

```
docs/01-requirements.md · docs/06-architecture.md
docs/harness/01-ssot.md · 02-verification.md · 03-loop.md · 04-human-decision.md
prisma/schema.prisma · scripts/verify/ 안의 모든 .ts
```

이 경로를 고쳐야 할 것 같으면 **고치기 전에 사람에게 말한다.** 원본 수정은 사람이 시작한다.

이미 고쳤다면 거기까지가 AI의 일이다. 무엇을 왜 고쳤는지 말하고, 실행할 명령을 알려 주고 멈춘다:

```
npm run verify:approve -- --scope <경로> "왜 바꾸는지"
```

**`verify:approve`를 대신 실행하지 않는다. 사람이 요청해도 실행하지 않는다.**
`protected.json`을 직접 편집하지도 않는다. 고친 사람과 승인한 사람이 갈라져야 승인이 검토의 자리를 지킨다.

## 4. 검증 루프 (03 §2)

```bash
npm run verify
```

### 4.1 attempt 세는 법 (03 §2.1)

> **1 attempt = 구현을 변경한 뒤 `npm run verify`를 한 번 실행해 결과를 얻은 것.**

* PASS도 FAIL도 1 attempt다. 첫 실행부터 1이다
* 실패 단계에 따라 나누지 않는다
* 중간에 끊기거나 실행이 시작조차 안 된 것은 세지 않는다
* CI 실행, 그리고 CI 실패를 재현하려 같은 커밋에서 돌린 로컬 실행은 세지 않는다

### 4.2 결과를 얻은 직후 상태를 기록한다 (03 §3)

```bash
gh issue comment <번호> --body '**[harness] 루프 상태**

- attempt: 2
- last_verify: FAIL (Test)
- needs_human: 없음'
```

* 필드는 **세 개만**이다. 최대 시도 횟수는 적지 않는다 — Issue 6번에서 읽는다
* `last_verify` 는 `PASS` 또는 `FAIL (단계명)`. 단계명은 02 §2의 이름을 쓴다
  (`Protected`·`Prepare`·`Types`·`Lint`·`Architecture`·`Test`·`Build`)
* **기존 상태 코멘트를 수정하지 않는다.** 매번 새로 추가하고, 마지막 것이 현재 상태다
* 이 기록이 있어야 세션이 끊겨도 다음 세션이 §0에서 이어받을 수 있다

### 4.3 다음 행동

```
결과를 얻음 → attempt +1 → 상태 코멘트
    │
    ├─ PASS ──────────────→ 로컬 루프 종료 → §5
    │
    └─ FAIL
         ├─ NEEDS_HUMAN ──→ 즉시 이탈 → §8
         ├─ 최대 횟수 도달 → 사람에게 넘긴다. 더 돌리지 않는다
         └─ 그 외 ────────→ 구현 수정 후 다시 §4
```

FAIL 후 다시 구현하는 것은 세 조건이 **모두** 참일 때다: FAIL이다 · `attempt < 최대` · NEEDS_HUMAN이 아니다.

### 4.4 실패 단계별 첫 행동 (02 §6)

| 단계 | 첫 행동 |
| --- | --- |
| Protected | **사람에게 확인한다.** 넘어가는 길은 없다 (§3.3) |
| Prepare | 스키마·마이그레이션·시드를 본다. 검증 로직 문제가 아니다 |
| Types / Lint | 코드를 고친다. **규칙을 끄지 않는다** |
| Architecture | 코드를 고친다. 재고 변경을 `applyMovement()` 안으로 옮긴다 |
| Test | **실패에 맞춰 테스트를 고치지 않는다.** 구현이 원본 규칙을 위반했는지 먼저 본다 |
| Build | 생성물·설정을 본다 |

> **검사를 통과시키기 위해 검사를 고치지 않는다.**

## 5. PR로 넘어간다

### 5.1 네 조건이 모두 참일 때만 연다 (03 §2.4)

1. 마지막 로컬 `npm run verify`가 **PASS**다
2. Issue 3번 **종료 조건이 전부 충족**됐다
3. **충족 결과를 Issue에 코멘트했다**
4. PR 본문이 `Closes #<번호>` 로 Issue를 연결한다

하나라도 아니면 PR을 열지 않는다. **PASS는 Issue 완료를 뜻하지 않는다.**

### 5.2 종료 조건 충족 코멘트 (조건 3)

§4.2의 루프 상태 코멘트와 **다른 것이다.** 마커나 형식이 정해져 있지 않으니 새로 만들지 않는다.
종료 조건 한 줄마다 **무엇을 근거로 충족됐다고 보는지** — 어느 테스트가 그것을 판정하는지 — 를 남긴다.

```bash
gh issue comment <번호> --body '종료 조건 충족 확인 (`npm run verify` PASS)

- [x] <종료 조건 1> — `tests/issues/issue-<번호>-<기능명>.test.ts` > "<it 이름>"
- [x] <종료 조건 2> — ...'
```

### 5.3 커밋 · 푸시 · PR

**verify가 PASS인 상태에서 한 번에 커밋한다.** 실패 상태를 이력에 남기지 않고,
그래야 03 §2.4-1(마지막 verify가 PASS)과 커밋 내용이 어긋나지 않는다.

```bash
git add -A
git status                      # 의도하지 않은 파일이 섞였는지 눈으로 본다
git commit -m "<type>(<scope>): <무엇을 했는지 한 줄>"
git push -u origin <브랜치>
gh pr create --title "<커밋 제목과 같은 한 줄>" --body "$(cat <<'EOF'
## 무엇을 바꿨는가
...

## 종료 조건
- [x] ...

Closes #<번호>
EOF
)"
```

`AGENTS.md` 맨 위 블록이 `next dev` 에 의해 다시 쓰여 uncommitted 상태로 나타날 수 있다.
그 변경은 작업과 함께 커밋해서 트리를 깨끗하게 둔다 (AGENTS.md 상단).

### 5.4 연 직후 링크를 확인한다 (03 §2.4-4)

본문에 문자열이 있는지가 아니라 **GitHub이 링크로 인식했는지**를 본다.

```bash
gh pr view <PR번호> --json closingIssuesReferences
```

비어 있으면 연결되지 않은 것이다. 본문을 고쳐 링크가 잡히게 한다.

### 5.5 CI가 실패하면 (03 §2.5)

**같은 커밋에서** 로컬 `npm run verify`를 돌려 재현되는지 본다. 이 실행은 attempt가 아니다.

* **CI와 같은 단계에서 같은 실패** → §4 루프로 복귀. attempt는 이어서 센다(0으로 초기화하지 않는다)
* **로컬은 PASS** → NEEDS_HUMAN
* **다른 실패가 났다** → NEEDS_HUMAN

이미 최대 시도 횟수를 소진했으면 복귀 즉시 사람에게 넘긴다.

## 6. 여기서 멈춘다

CI가 PASS면 그 PR은 **사람의 판단을 기다리는 상태**다. 이 스킬의 끝이다.

**AI는 다음을 하지 않는다** (04 §3):

* `gh pr merge` — **승인은 사람의 행위다**
* `gh pr close` — **반려는 사람의 행위다**
* 판단을 기다리지 않고 다음으로 진행하는 것

저장소에 이것을 강제하는 장치는 없다. 브랜치 보호도 룰셋도 없고 AI와 사람이 같은 토큰을 쓴다.
**규약이 지킨다.** CI PASS는 검증을 통과했다는 뜻일 뿐 승인이 아니다.

사람에게 PR 링크와 함께 남은 판단이 무엇인지 알리고 끝낸다.

## 7. 반려된 PR을 다시 잡을 때 (04 §5·§6)

### 7.1 이번 반려 주기의 코멘트만 본다 (04 §5.2)

> **반려 주기 = 가장 최근 reopen 이후부터 현재 Close 까지.**

이전 주기의 반려 사유를 지금 사유로 재사용하지 않는다.

```bash
PR=<번호>
REPO=$(gh repo view --json nameWithOwner --jq .nameWithOwner)
FROM=$(gh api repos/$REPO/issues/$PR/timeline --paginate \
  --jq '[.[] | select(.event=="reopened") | .created_at] | last // ""')
TO=$(gh pr view $PR --json closedAt --jq .closedAt)
gh api repos/$REPO/issues/$PR/comments --paginate \
  --jq "[.[] | select(.created_at > \"$FROM\" and .created_at <= \"$TO\")
        | select(.body | startswith(\"**[harness] 반려**\"))] | last"
```

* 마커가 있고 `반려 사유`·`걸린 종료 조건`이 **둘 다** 있으면 유효하다 (여럿이면 마지막 것)
* 주기 안에 없거나 항목이 빠졌으면 **NEEDS_HUMAN**이다 → §8
* **반려 사유를 추측해서 재구현하지 않는다** (04 §5.4)

### 7.2 순서를 바꾸지 않는다 (04 §6)

```
① attempt 를 0 으로 초기화
② Issue 에 루프 상태 코멘트 (아래 형식)
③ gh pr reopen <번호>
④ §4 구현·검증 루프로 복귀 — 1 회차부터
⑤ 03 §2.4 네 조건을 다시 충족하면 §6 판단 대기로
```

**②가 ③보다 앞선다.** reopen이 먼저 되면 PR이 `OPEN`이 되어, 그사이 세션이 끊기면
다음 세션이 §0에서 이것을 "판단 대기"로 오독한다. 기록이 먼저 남아야 그 창이 닫힌다.

```
**[harness] 루프 상태**

- attempt: 0
- last_verify: <반려 직전 마지막 값을 그대로 옮긴다>
- needs_human: 없음

사람 반려로 구현 루프에 재진입했다. attempt 를 0 으로 초기화했다.
`last_verify` 는 반려 직전에 마지막으로 얻은 결과이며, 지금 상태가 아니다.
반려 사유: #<PR번호> 의 `**[harness] 반려**` 코멘트 — <URL>
```

* **반려 사유 원문을 Issue에 옮겨 적지 않는다.** 원본은 PR 코멘트이고 Issue에는 참조만 남긴다
* **새 PR을 만들지 않는다.** 재구현은 같은 PR에 이어서 반영한다
* reopen이 실패하면(대개 head 브랜치가 삭제된 경우) **NEEDS_HUMAN**이다. 새 브랜치로 우회하지 않는다
* 사람 반려만 attempt를 0으로 초기화한다. CI 실패 복귀(§5.5)는 초기화하지 않는다

## 8. NEEDS_HUMAN

**어느 쪽이 맞는지 스스로 고르지 않는다.** 더 그럴듯한 쪽, 더 최근인 쪽, 코드와 맞는 쪽으로 정하지 않는다.

선언하는 경우:

* Issue ↔ 원본 충돌, 원본 ↔ 원본 충돌 (SSOT §4)
* CI 실패가 로컬에서 재현되지 않음 (03 §2.5)
* 반려 코멘트가 없거나 항목이 빠짐 (04 §5.4)
* reopen 실패 (04 §6.3)

선언은 §4.2 형식의 루프 상태 코멘트로 남기고 `needs_human: 있음` 으로 적는다.
문서·원본 충돌이면 세 가지를 함께 적는다 (SSOT §4):

1. 충돌한 두 곳의 위치 — 파일과 절, 또는 Issue 번호
2. 각각이 무엇이라고 말하는지 — 원문 인용
3. 무엇이 정해져야 진행할 수 있는지

선언한 뒤에는 **그 판단에 의존하는 작업을 하지 않는다.** 무관한 부분은 진행할 수 있고,
무엇을 남겨 뒀는지 밝힌다. 사람에게도 같은 내용을 보고한다.

## 자주 어긋나는 지점

* **PASS ≠ 완료.** Issue 종료 조건이 완료를 정한다 (03 §2.3)
* **CI PASS ≠ 승인.** 승인은 사람의 Merge다 (04 §2)
* 루프 상태 코멘트와 종료 조건 충족 코멘트는 **다른 것**이다 (§4.2 / §5.2)
* 상태 코멘트는 **수정하지 않고 추가**한다
* 보호 경로 승인은 **사람이 직접** 실행한다
* 반려 후에만 attempt가 0이 된다. CI 복귀는 아니다
